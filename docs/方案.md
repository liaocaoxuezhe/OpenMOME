# OpenMOME 方案（MVP 版）

> 版本：v0.1（MVP，已实现；M0 实测后修正了性能目标）｜日期：2026-10-10｜作者：Claude（与项目所有者共同确认）
>
> 一句话定位：**本地运行的个人 Web 工具——粘贴小宇宙 / YouTube / B站链接，拿到带时间戳的逐字稿和一份结构化分析笔记。有字幕就直接用字幕，没字幕才下载音频、在本机转写。**

---

## 0. 需求解读（先对齐口径）

| 原话 | 本方案的理解 |
|---|---|
| "下载视频，然后进行**撰写**和分析" | "撰写"按**转写**（语音转文字）理解：下载 → 转写 → 分析 |
| "如果 B站和 YouTube 有字幕文件，就不需要这个东西了，也不需要撰写了" | 有可用字幕时，**跳过下载和转写**，直接用字幕做分析；**分析步骤仍然执行** |
| "下载视频" | MVP **只下载音频**（转写只需要音频，体积约为视频的 1/10~1/30，磁盘紧张）；保留视频放到后续版本 |
| "第一版固定最合适的模型，后续再支持可选模型" | MVP 中 ASR 模型、LLM 均写死为一套默认组合，但代码层面预留接口（Provider 抽象），后续加选项不用重构 |
| "满足自己日常使用" | 单用户、本机访问（`127.0.0.1`），不做账号体系、不做公网部署 |

## 1. 现状

### 1.1 本机环境（2026-10-10 实测）

| 项 | 实测结果 | 对方案的影响 |
|---|---|---|
| 机型 / 芯片 | MacBook Pro，**Apple M4**（10 核 CPU：4P+6E，10 核 GPU） | ⚠️ 不是 M4 Pro。调研文档里的 RTF 数据是 M4 Pro 上的，本机 GPU 核数约为 M4 Pro 的一半，**预估速度慢 1.5~2 倍**，需 M0 阶段实测 |
| 内存 | 16 GB 统一内存（CPU/GPU 共享，模型实际可用约 10~12 GB） | ASR 与 LLM 不能同时在本机大模型上跑；任务必须**串行** |
| 磁盘 | 460 GB，**剩余约 23 GB（已用 95%）** | 模型 + 依赖约 7~8 GB；音频必须有清理策略 |
| 系统 Python | 3.9.13 | ❌ 不满足 `mlx-qwen3-asr` 要求（≥3.10）和 pyannote.audio 4.x 要求 → **必须用虚拟环境** |
| 其他 Python | `python3.11`（~/.local/bin）、`python3.12`（Homebrew）、`uv` 已安装 | 用 `uv` 创建 Python 3.11 虚拟环境 |
| ffmpeg | 已安装（Homebrew） | 直接用 |
| yt-dlp | 未安装 | 作为项目依赖装进虚拟环境 |
| Ollama | 已安装，仅有 ≤2B 的小模型 | 小模型不足以总结 1 小时以上的长逐字稿，MVP 不用本地 LLM（理由见 §4.4） |
| Node | v22 | MVP 前端不需要构建工具，用不上 |
| 项目目录 | `OpenMOME/` 为空目录，非 git 仓库 | 从零搭建 |

### 1.2 已有调研结论（Notion：开源语音转写 + 说话人识别调研 2026-10）

- 最佳本地组合：**Qwen3-ASR（MLX）+ Qwen3-ForcedAligner-0.6B + pyannote community-1**，均可商用。
- 通过 `mlx-qwen3-asr`（当前 0.4.4，Apache-2.0）一个包即可完成"转写 + 词级时间戳 + 说话人分离"。
- 中文准确率显著优于 Whisper（WenetSpeech meeting 错误率 5.88 vs 19.11）。
- 所有方案对**多人重叠说话**都弱。

### 1.3 参考项目 BiliNote 的可借鉴点与不足

| 维度 | BiliNote | 本项目取舍 |
|---|---|---|
| 架构 | FastAPI 后端 + React/Vite 前端 + Tauri 桌面端 + 浏览器扩展 | 只借鉴后端分层；前端大幅简化（个人使用无需构建链） |
| 平台 | B站、YouTube、抖音、快手、本地文件 | 只做 **小宇宙、YouTube、B站** |
| 字幕优先 | B站、YouTube 都先取字幕 | ✅ 照搬思路 |
| 转写 | Faster-Whisper、MLX-Whisper、Groq、必剪等 | 换成 **Qwen3-ASR**（中文更好，BiliNote 没有） |
| 说话人 | 无 | ✅ 新增（播客是多人对话，必须要） |
| 小宇宙 | 未支持 | ✅ 新增 |
| 笔记 | 9 种风格、截图、思维导图、RAG 问答 | MVP 只做 1 种固定模板，其余进路线图 |

### 1.4 三个平台的现状（实测 / 查证）

| 平台 | 字幕获取 | 音频获取 | 关键约束 |
|---|---|---|---|
| **小宇宙** | 官方文字稿接口需要登录态；登录态自动化有**账号风控/封号**风险（xyz-dl 作者明确警告） | 单集页面 HTML 内 `<script id="__NEXT_DATA__">` → `props.pageProps.episode.enclosure.url`（公开单集，免登录） | MVP **不取官方文字稿，一律本地转写**；付费单集（`private-media.xyzcdn.net`）不支持 |
| **YouTube** | yt-dlp 可取人工字幕和自动字幕 | yt-dlp `bestaudio` | 2025 年底起 yt-dlp 需要外部 JS 运行时（推荐 **Deno**）才能完整支持 YouTube，否则可能 403 |
| **B站** | `api.bilibili.com/x/player/wbi/v2` 返回 `subtitle.subtitles[]`，需要 **WBI 签名**；**不带 SESSDATA Cookie 基本拿不到**（含 AI 字幕 `ai-zh`） | yt-dlp `bestaudio` | 需要用户在 `.env` 配置自己的 B站 Cookie；没配就退回本地转写 |

## 2. 目标与成果

### 2.1 MVP 要达成的成果

1. 运行 `./start.sh` 后，浏览器打开 `http://127.0.0.1:8765`。
2. 页面上粘贴一个链接（小宇宙 / YouTube / B站），点"开始"。
3. 页面实时显示进度：`解析链接 → 获取字幕 / 下载音频 → 转写 → 生成笔记 → 完成`。
4. 完成后可以看到并下载三样东西：
   - **逐字稿**：带时间戳，播客类带说话人（S1/S2…），可下载 `.md` / `.srt` / `.json`
   - **分析笔记**：Markdown，固定模板（见 §4.5），时间戳可点击跳回原视频/原节目对应位置
   - **来源信息**：标题、作者、时长、发布时间、原链接、文字来源（"平台字幕"或"本地转写"）
5. 历史记录列表：看过的任务都在，可以重新打开、重新生成笔记、删除。

### 2.2 非目标（MVP 明确不做）

- 多用户、登录、公网部署、移动端适配
- 视频截图插入笔记、思维导图、RAG 问答
- 多种笔记风格、模型下拉选择（只预留接口）
- 批量 / 订阅 / 定时抓取（避免触发平台风控）
- 小宇宙付费单集、B站大会员/充电专属内容
- 实时流式转写

### 2.3 质量目标

| 指标 | 目标 |
|---|---|
| 1 小时中文播客端到端耗时（本机 M4） | ~~≤ 15 分钟~~ → **1.7B ≤ 30 分钟 / 0.6B ≤ 15 分钟**（M0 实测修正，见 docs/benchmark.md） |
| 有字幕的 YouTube / B站视频端到端耗时 | ≤ 2 分钟（不含 LLM 排队） |
| 中文转写质量 | 主观抽查：专有名词外基本可读，无大段幻觉/重复 |
| 峰值内存 | 转写阶段进程峰值 ~~≤ 8 GB~~ → **≤ 9 GB**（MLX 缓冲池限 1GB 后实测 8.8GB） |
| 稳定性 | 单个任务失败不影响服务；重启服务后历史任务仍可查看 |

## 3. 总体架构

### 3.1 架构图

```
┌──────────────────────── 浏览器 (127.0.0.1:8765) ────────────────────────┐
│  单页：链接输入框 · 进度条 · 逐字稿/笔记 双标签页 · 历史列表               │
└───────────────┬───────────────────────────────────────▲──────────────────┘
                │ POST /api/tasks                       │ GET /api/tasks/{id}（2s 轮询）
┌───────────────▼───────────────────────────────────────┴──────────────────┐
│ FastAPI（app/main.py）                                                    │
│   ├─ api/         路由层：创建任务、查询、重新生成、删除、下载文件         │
│   ├─ worker       单线程任务队列（同一时刻只跑 1 个任务）                  │
│   └─ pipeline     流水线编排（每步写状态到 SQLite）                        │
│        │                                                                  │
│        ├─ 1 resolver      识别平台、规范化链接、取元数据                   │
│        ├─ 2 subtitles     字幕优先：YouTube(yt-dlp) / B站(WBI API)         │
│        ├─ 3 downloader    无字幕时下载音频：yt-dlp / 小宇宙直链            │
│        ├─ 4 audio         ffmpeg → 16kHz 单声道 wav                        │
│        ├─ 5 asr           子进程调用 mlx-qwen3-asr（转写+时间戳+说话人）   │
│        ├─ 6 transcript    统一成 Segment 结构，导出 md/srt/json            │
│        └─ 7 llm           OpenAI 兼容接口生成分析笔记（长文本分段汇总）    │
└───────────────┬──────────────────────────────────────────────────────────┘
                │
   data/openmome.db（SQLite：任务、状态、元数据）
   data/tasks/<task_id>/（audio.m4a, transcript.json/.md/.srt, note.md, log.txt）
   ~/.cache/huggingface（Qwen3-ASR-1.7B、ForcedAligner-0.6B、pyannote 模型）
```

### 3.2 技术选型与理由

| 层 | 选型 | 为什么 |
|---|---|---|
| 运行环境 | `uv` + **Python 3.11** 虚拟环境（`.venv/`） | 系统 3.9 不满足 mlx-qwen3-asr / pyannote 4.x 的 ≥3.10 要求；本机已有 3.11 和 uv，不污染系统环境 |
| Web 后端 | **FastAPI** + Uvicorn | 与 BiliNote 同栈，异步、自带 OpenAPI 文档，便于后续扩展 |
| 前端 | **单个 HTML + 原生 JS + marked.js**，由 FastAPI 静态托管 | 个人工具，没有必要引入 React/Vite 构建链；改一个文件刷新即可；后续需要再升级 |
| 任务调度 | 进程内**单线程队列**（`queue.Queue` + 1 个 worker 线程） | 16GB 内存不允许并发转写；单用户不需要 Celery/Redis；简单可靠 |
| 持久化 | **SQLite**（标准库 `sqlite3`）+ 任务目录文件 | 零部署；逐字稿等大文本放文件，库里只存状态与元数据 |
| 进度推送 | 前端 2 秒**轮询** | 比 SSE/WebSocket 简单，个人使用延迟完全可接受 |
| 链接解析/下载 | **yt-dlp**（YouTube、B站）+ **httpx**（小宇宙、B站字幕 API） | yt-dlp 是事实标准，维护活跃；小宇宙不在 yt-dlp 支持范围内，自己解析 `__NEXT_DATA__` |
| YouTube JS 运行时 | **Deno**（`brew install deno`） | yt-dlp 当前推荐的方案，解决签名/nsig 导致的 403 |
| 音频处理 | **ffmpeg**（已安装） | 统一转 16kHz 单声道 wav，这是 ASR 的标准输入 |
| ASR | **mlx-qwen3-asr** + `Qwen/Qwen3-ASR-0.6B`（2026-10-10 由 1.7B 改为默认 0.6B，见 docs/benchmark.md §6）+ `Qwen3-ForcedAligner-0.6B` + `pyannote/speaker-diarization-community-1`（与转写并行，MPS） | 见 §4.3 |
| LLM | **OpenAI 兼容接口**，MVP 固定 **DeepSeek**（具体模型名写在 `.env`） | 见 §4.4 |

## 4. 实现方案

### 4.1 链接识别（resolver）

按正则匹配，统一输出 `{platform, canonical_url, id}`：

| 平台 | 支持的链接形式 | 规范化 |
|---|---|---|
| 小宇宙 | `xiaoyuzhoufm.com/episode/<24位hex>` | 只取 episode id；**节目主页链接（/podcast/）给出明确提示"请粘贴单集链接"** |
| YouTube | `youtube.com/watch?v=`、`youtu.be/`、`/shorts/`、`/live/` | 只保留 `v=`，去掉 `list=`/`t=` 等参数，**不展开播放列表** |
| B站 | `bilibili.com/video/BV…`、`av…`、`b23.tv/…` 短链 | 短链先跟随跳转；保留 `?p=N` 分P；默认 P1 |

识别失败直接在前端报错，不建任务。

### 4.2 字幕优先策略（核心分支）

```
有平台字幕且质量可接受？ ──是──► 解析成 Segment ──► 直接进入 LLM 分析（跳过下载、转写）
        │否 / 用户勾选"强制本地转写"
        ▼
下载音频 ──► 本地转写 ──► LLM 分析
```

**字幕选择优先级（MVP 固定规则）：**

| 平台 | 优先级 | 说明 |
|---|---|---|
| YouTube | ① 人工字幕：视频原语言 → `zh-Hans` → `zh` → `zh-Hant` → `en`<br>② 自动字幕：仅限**视频原语言**的自动字幕<br>③ 都没有 → 本地转写 | 不用"自动翻译"字幕（质量差）；中文视频的 YouTube 自动字幕质量通常一般，前端提供**"强制本地转写"复选框**兜底 |
| B站 | ① UP 主上传的 CC 字幕（`lan` 非 `ai-` 开头）<br>② AI 字幕 `ai-zh`<br>③ 无 Cookie / 无字幕 → 本地转写 | 调用 `x/player/wbi/v2?bvid=&cid=` 需 WBI 签名（从 `x/web-interface/nav` 取 `img_key`/`sub_key` 计算 `w_rid`），请求带 `.env` 中的 `BILIBILI_SESSDATA` |
| 小宇宙 | 直接本地转写 | 官方文字稿依赖登录态，有封号风险，MVP 不碰 |

**字幕健全性检查**（防止拿到空字幕或错配字幕）：字幕覆盖时长 < 视频时长 50%，或总字数过少（< 时长分钟数 × 30 字）时，视为不可用，自动改走本地转写，并在日志里记录原因。（B站充电视频的 AI 字幕有错配案例，此检查兜底一部分。）

### 4.3 本地转写（ASR）

**固定组合：**

| 组件 | 模型 | 作用 | 内存 |
|---|---|---|---|
| 识别 | `Qwen/Qwen3-ASR-1.7B` | 语音转文字，自动语种识别（中/英/粤/方言） | ~3.4 GB |
| 对齐 | `Qwen/Qwen3-ForcedAligner-0.6B`（`--timestamps`） | 词级时间戳 → 句级时间戳 | ~1.2 GB |
| 说话人 | `pyannote/speaker-diarization-community-1`（`--diarize`） | 区分 S1/S2/… | 小（MPS） |

**为什么选 1.7B 而不是 0.6B：** 本工具是离线批处理、不是实时；1.7B 中文准确率更高，内存 3.4GB 在 16GB 机器上可以接受。即使本机比 M4 Pro 慢 2 倍，RTF 约 0.15，1 小时音频约 9 分钟，可接受。M0 实测若明显超标，再降为 0.6B。

**为什么用子进程调 CLI，而不是在 FastAPI 进程里 `import`：**
1. **内存隔离**：转写结束子进程退出，3~5GB 内存立刻全部归还；常驻进程里 MLX/torch 的缓存不一定能及时释放。
2. **崩溃隔离**：模型 OOM 或 Metal 报错只会让子进程失败，Web 服务不受影响。
3. **超时可控**：子进程可以按时长设超时并强制结束。
4. 代价是每次多几秒模型加载时间，对分钟级任务可以忽略。

调用形式（实际参数以 M0 实测的 CLI 为准）：

```bash
.venv/bin/mlx-qwen3-asr data/tasks/<id>/audio.wav \
  --model Qwen/Qwen3-ASR-1.7B \
  --timestamps --diarize --diarize-device mps \
  -f json -o data/tasks/<id>/asr/
```

- **说话人数**：默认不指定，由 pyannote 自动估计；前端提供可选的"说话人数"输入框（填了就传 `--num-speakers`）。
- **说话人分离开关**：小宇宙默认开；YouTube/B站默认关（多为单人讲解，省时间）；前端可切换。
- **没配 HF Token** 时：自动降级为"只转写不分离说话人"，并在页面提示。
- **长音频**：mlx-qwen3-asr 内部按低能量点切成 30 秒块并逐块释放内存，2~3 小时音频无需额外处理。
- **超时**：音频时长 × 0.5 + 5 分钟。

### 4.4 LLM 分析

**MVP 固定方案：DeepSeek，走 OpenAI 兼容接口。**

为什么不用本地 LLM：

| 考虑 | 说明 |
|---|---|
| 上下文长度 | 1 小时中文播客逐字稿约 1.5~2 万字，2 小时约 3~4 万字。本地 7~8B 模型开 32K 上下文，在 16GB 机器上 KV cache 占用大、速度慢 |
| 质量 | 本机 Ollama 现有模型都 ≤2B，不足以做长文本结构化分析；8B 级本地模型的总结质量也明显不如云端大模型 |
| 内存 | 转写阶段已占 4~5GB，再加本地 LLM 容易触发内存压力和 swap |
| 成本 | DeepSeek 处理一期播客的费用很低，个人日常使用可以忽略 |

需要说明：**逐字稿会发送到 DeepSeek 服务器。** 若个别内容不想外发，后续版本把 `LLM_BASE_URL` 指向本机 Ollama 即可（同一套 OpenAI 兼容代码，无需改动）——这就是"后续支持可选模型"的扩展点。

**长文本处理（按长度自动选择）：**

```
逐字稿字数 ≤ 4 万字 ──► 单次调用生成笔记
逐字稿字数 > 4 万字 ──► Map：按时间切成约 20 分钟一段，每段生成"段落要点+时间戳"
                       Reduce：汇总各段要点生成最终笔记
```

输入给 LLM 的逐字稿格式：`[mm:ss] S1: 文本`，让模型输出的时间戳可以落在真实位置上。

**API 密钥管理：** 只放 `.env`（`DEEPSEEK_API_KEY`），代码中通过环境变量读取，**不写进代码、不存数据库、不在前端展示**。

### 4.5 笔记模板（MVP 固定一种）

```markdown
# {标题}
> 来源：{平台} · {作者} · {时长} · {发布日期} · [原链接]({url})
> 文字来源：平台字幕 / 本地转写（Qwen3-ASR-1.7B）

## 一句话总结
## 核心观点（3~7 条，每条附 [mm:ss] 时间戳）
## 内容脉络（按时间分章节：[mm:ss] 章节标题 + 2~4 句要点）
## 关键论据与案例
## 金句摘录（原话 + 时间戳 + 说话人）
## 提到的人物 / 书籍 / 产品 / 术语
## 分析与思考（论证是否充分、有无漏洞、可行动建议、值得追问的问题）
```

- 时间戳渲染为链接：YouTube `&t=123s`，B站 `?t=123`，小宇宙无法定位到秒，只显示文本。
- 说话人在笔记里保留 S1/S2；"根据上下文推断真实姓名"放到后续版本（容易推断错，MVP 先不做）。
- prompt 存在 `app/llm/prompts/note.md`，改模板不用改代码。

### 4.6 统一数据结构

```python
class Segment:
    start: float     # 秒
    end: float
    speaker: str | None   # "S1"… 或 None
    text: str

class Transcript:
    source: Literal["platform_subtitle", "local_asr"]
    language: str
    segments: list[Segment]
```

所有来源（YouTube vtt、B站字幕 json、ASR json）都先转成这个结构，后面的导出和 LLM 只认这一种格式。

### 4.7 任务状态机

```
queued → resolving → fetching_subtitle ─┬─(有字幕)──────────────────────► summarizing → done
                                         └─(无字幕) downloading → transcribing ─┘
任意步骤异常 → failed（记录 error_stage + error_message + log.txt）
```

- 每一步完成后把产物写入任务目录。**"重新生成笔记"只重跑 `summarizing`**，不重新下载和转写。
- 服务重启时，处于中间状态的任务标记为 `failed (interrupted)`，可手动重试。
- 同一链接再次提交：提示"已有结果"，可选择查看或重新处理。

## 6. 注意事项与风险

### 6.1 环境与资源

| 风险 | 应对 |
|---|---|
| **磁盘只剩约 23GB** | 模型 + torch 等依赖约 7~8GB，安装前确认空间；只下载音频不下视频；转写完成即删除中间 `wav`；`KEEP_AUDIO=false` 时删除原始音频；健康检查显示剩余空间，**低于 5GB 拒绝新任务** |
| **芯片是 M4 不是 M4 Pro** | 调研文档的 RTF 不能直接套用，以 M0 实测为准；超标时降级到 0.6B |
| 16GB 内存 | 任务严格串行；ASR 用子进程；转写期间避免同时跑其他大模型 |
| Python 3.9 系统环境 | 全部在 `.venv`（3.11）内运行；`start.sh` 强制使用 `.venv/bin/python` |
| pyannote 依赖 torch（体积大） | 已计入空间预算；未来如果不需要说话人分离，可以去掉 `[diarize]` 依赖 |

### 6.2 平台相关

| 风险 | 应对 |
|---|---|
| YouTube 反爬频繁变化（403、PO Token） | 安装 Deno；`yt-dlp` 不锁死版本，README 提供 `uv pip install -U yt-dlp` 一键更新；健康检查显示 yt-dlp 版本 |
| B站需要 Cookie 才能拿字幕 | 用户自行从浏览器复制 SESSDATA 填到 `.env`；**Cookie 等同于登录凭证，只放本地 `.env`，不入库、不打日志**；Cookie 过期时自动降级为本地转写并提示 |
| 小宇宙页面结构可能变化 | 解析逻辑集中在 `xiaoyuzhou.py` 一处；用保存的页面样本做单元测试；解析失败给出明确报错 |
| 平台风控 | 只做单链接手动提交，不做批量/订阅；小宇宙不使用登录态 |
| 版权 | 仅限个人学习使用；下载的音频默认处理完即删除；不提供公开分享功能 |

### 6.3 质量相关

| 风险 | 应对 |
|---|---|
| 多人重叠说话时说话人分离不准 | 已知限制，页面注明；说话人标签仅供参考 |
| 专有名词识别错 | MVP 由 LLM 在笔记中顺带纠正；后续版本加"热词/上下文"（mlx-qwen3-asr 支持 `--context`） |
| 平台自动字幕质量差 | 健全性检查 + "强制本地转写"开关 |
| LLM 编造时间戳或内容 | prompt 要求时间戳只能取自输入；后端校验时间戳不超出总时长，超出的去掉链接 |
| 逐字稿外发到云端 LLM | 方案中已明示；后续可切换本地 Ollama |

### 6.4 安全

- 服务只绑定 `127.0.0.1`，不暴露到局域网。
- 所有密钥（DeepSeek Key、HF Token、B站 SESSDATA）只放 `.env`，`.gitignore` 忽略；日志中做脱敏。
- 下载 URL 只接受上述三个平台域名，防止被当作任意 URL 下载器。
- 所有文件读写使用 UTF-8（中文标题、文件名安全处理：任务目录用 task_id，不用标题当文件名）。
